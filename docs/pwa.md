# EduNivo PWA

EduNivo can be installed as an app on Android, iPhone/iPad, Windows, macOS, ChromeOS and Linux. It installs from the same Next.js codebase as the website, with no separate native project. Once installed, it opens in its own window with no address bar, tabs or browser buttons.

The PWA layer is additive. Routing, auth, permissions, APIs and business logic are unchanged, and nothing renders until the install dialog opens or an update is waiting.

## Architecture

## Installation flow

```
Login → protected layout mounts → InstallPromptGate starts a 4.5 s timer
      → shouldAutoShowInstallPrompt()?
           running as app?            → no
           "Maybe Later" < 7 days ago → no
           already shown this tab     → no
           Chromium: beforeinstallprompt captured? → yes
           iOS / macOS Safari: not marked installed? → yes
      → InstallModal opens
```

- **One rule for every role.** The gate only renders inside the protected layouts (dashboard and super-admin), so placement guarantees the user is authenticated. There is no per-role logic, and future roles get the dialog automatically.
- **Capturing the browser event.** `installPromptStore.ts` listens for `beforeinstallprompt` at module evaluation, not in a `useEffect`. The browser can fire it once, before React hydrates. The handler calls `preventDefault()` to suppress Chrome's mini-infobar.
- **Install Now** calls the stored event's `prompt()` inside the click handler. The event is single-use. If the user declines the native prompt, it counts as "Maybe Later".
- **Maybe Later**, the close button, Esc and a backdrop click all snooze the automatic dialog for 7 days (`INSTALL_SNOOZE_MS`). The dialog also opens at most once per tab session.
- **Permanent profile-menu entry.** The user menu (desktop) and profile sheet (mobile) always show it. In a browser tab it reads "Download app" or "Open App". Inside the installed app window it becomes a non-clickable **"You're using the Desktop App"** status row. What the dialog shows depends on the current `InstallMode` (see `installContext.tsx`):
  - `prompt`: Chromium offered `beforeinstallprompt`. The dialog shows the 7 benefits, with **Download & Install EduNivo** (native prompt) and **Continue in Browser**. After a successful install, a toast says "EduNivo has been installed successfully."
  - `ios` / `macos-safari`: Share → Add to Home Screen / File → Add to Dock steps.
  - `installed`: the app is already on this device. **Open App** launches it through the `web+edunivo://` link handler registered in the manifest (`protocol_handlers`, see `src/pwa/appLauncher.ts`). This works in Chromium on desktop, and Chrome asks the user to allow it the first time. If the window doesn't lose focus within 2 s, the dialog falls back to "Open in app" in the address bar and the Start menu, Dock or home screen. An app installed before `protocol_handlers` existed picks it up after Chrome refreshes the installed manifest, which happens on a later app launch. **"See how to install"** covers a stale "installed" record.
  - `browser-menu`: no one-click install is available (Firefox, or a Chromium tab that isn't eligible yet). The install button is hidden and an informational message appears instead: browser-menu steps on Chromium, or "open in Chrome, Edge or Brave" elsewhere. The only button is **Continue in Browser**.

  The mode is captured when the dialog opens, so its content never flips mid-install.
- **`appinstalled`** stores `sms_next_pwa_installed` and closes everything.

### Already-installed detection

| Signal | Platforms |
|---|---|
| `display-mode: standalone / fullscreen / minimal-ui / window-controls-overlay` media query | All, when running as the app |
| `navigator.standalone` | iOS home-screen app |
| `document.referrer` starts with `android-app://` | Android TWA wrappers |
| `beforeinstallprompt` **does not fire** once installed | Chromium (Android, Windows, macOS, ChromeOS, Linux) |
| `navigator.getInstalledRelatedApps()` (manifest lists itself in `related_applications`) | Chromium. Catches installs made via the browser UI. Best effort: an app installed before this field existed reports nothing until Chrome refreshes its manifest |
| `appinstalled` event and the stored `sms_next_pwa_installed` flag | Chromium. On Safari, set by the user's "I've added it" |

On Chromium, the browser's own event is the source of truth. A stale stored flag is overridden as soon as `beforeinstallprompt` fires again, for example after an uninstall.

## Browser compatibility

| Platform / browser | Install path | Experience |
|---|---|---|
| Chrome, Edge, Brave, Opera (Windows, macOS, Linux, ChromeOS) | `beforeinstallprompt` | Custom dialog → native prompt → own window |
| Chrome, Samsung Internet, Edge (Android) | `beforeinstallprompt` | Custom dialog → native prompt → home screen |
| Safari, Chrome, Edge, Firefox (iOS / iPadOS 16.4+) | Manual | Dialog with Share → Add to Home Screen steps |
| Safari 17+ (macOS Sonoma+) | Manual | Dialog with File → Add to Dock steps |
| Firefox (desktop) | None | No dialog, no menu entry. Site works as before |
| In-app webviews (Instagram, Facebook, LinkedIn…) | None | No dialog |

iPadOS reports a Mac user agent. It's detected as iOS by `Macintosh` plus `navigator.maxTouchPoints > 1`.

## iOS limitations

- No `beforeinstallprompt` and no install API, so the user must use the Share menu. `IOSInstallGuide` explains the steps.
- No API reports whether the app is on the home screen. After "Maybe Later", the guide returns after 7 days unless the user taps **"I've added it"**.
- A home-screen app has **storage separate from Safari**. The user signs in again inside the app, and opening the app can't tell the Safari tab it was installed.
- iOS ignores most of the manifest's look. The `appleWebApp` metadata in `layout.tsx` (title, status bar style) and `app/apple-icon.png` control it. The status bar style is `default`, so content never slides under the notch on pages without safe-area padding.
- iOS shows no splash screen without per-device `apple-touch-startup-image` assets (see "Future enhancements").

## Manifest configuration

`src/app/manifest.ts` is served at `/manifest.webmanifest`, and Next adds `<link rel="manifest">` to every page.

| Field | Value | Why |
|---|---|---|
| `id`, `start_url`, `scope` | `/` | `/` already routes to `/dashboard`, `/super-admin` or `/login` |
| `display` | `standalone` | Own window, no browser UI |
| `orientation` | `any` | Tablets and desktops are used in landscape |
| `theme_color` | `#5048e5` (`--primary`) | App title bar and Android status bar |
| `background_color` | `#eff0f6` (`--background`) | Android splash screen |
| `launch_handler` | `navigate-existing` | Clicking the icon focuses the open window instead of opening a second one |
| `protocol_handlers` | `web+edunivo` → `/?launch=%s` | Lets a browser tab's **Open App** button launch the installed app |
| `icons` | 72–512 `any` + 192/512 `maskable` | Maskable icons keep the logo inside the 80% safe zone |
| `shortcuts` | Dashboard, Notices, Communication | Routes every school role can open |

No `<meta name="theme-color">` is set on pages, so browser tabs look exactly as before. Only the installed window uses the brand color.

**Icons.** `npm run pwa:icons` renders every icon from one SVG: the same white graduation cap on the primary→accent gradient used by the sidebar logo. It uses `sharp`, which ships with Next.js. Re-run it only when the logo or brand colors change, and commit the output. Keep the colors in `scripts/generate-pwa-icons.mjs` and `src/pwa/config.ts` in sync with `globals.css`.

## Offline strategy

| Request | Strategy | Notes |
|---|---|---|
| `/api/*` | **Never cached** (not intercepted) | Authenticated, per-user data. Caching it would risk serving stale data or another user's data |
| Non-GET, cross-origin (Cloudinary, Razorpay…) | Not intercepted | |
| Page navigations | Network-first → cached copy of the route → `/offline.html` | Uses navigation preload. Keeps the last 40 routes |
| `/_next/static/*` (JS, CSS, fonts) | Cache-first | Content-hashed, so the files are immutable |
| Images, icons, fonts, manifest | Stale-while-revalidate | |
| Everything else (RSC payloads, `/_next/image`) | Network | |

Caching page HTML is safe here because every page is a client component, and user data is loaded from `/api` with the bearer token stored in localStorage. The cached HTML is a data-free app shell. **If you add a Server Component that renders per-user data, exclude its route from the page cache in `src/pwa/sw.js`.**

When offline, previously visited pages still open. Data requests fail through the existing `apiGet`/`apiPost` error handling ("Could not reach the server…"). Pages never visited show `offline.html`, which reloads automatically when the connection returns.

## Service worker lifecycle

1. **Build.** `npm run build` runs `prebuild`, which runs `scripts/build-sw.mjs`. It copies `src/pwa/sw.js` to `public/sw.js` with a unique `VERSION` (commit SHA on Vercel, plus a timestamp). A byte-different worker per deploy is what lets browsers detect updates. `public/sw.js` is generated and gitignored. Edit `src/pwa/sw.js` instead.
2. **Register.** `PWAProvider` calls `navigator.serviceWorker.register("/sw.js", { scope: "/", updateViaCache: "none" })`. This happens in **production builds only**, because a caching worker would fight Turbopack's HMR in `next dev`.
3. **Install.** The worker precaches `offline.html`, the manifest, the favicon and the core icons into `edunivo-precache-<version>` (essential: a failure aborts the update). It then **downloads the new app shell in the background**, on a best-effort basis: it fetches `/login` and `/dashboard`, caches their HTML, and caches every `/_next/static` chunk they reference. By the time the update banner appears, the new version is already on the device.
4. **Activate.** It deletes every `edunivo-*` cache from other versions, enables navigation preload, and claims open pages.
5. **Update.** A new worker installs alongside the old one and **waits**. It doesn't call `skipWaiting()` on its own, so an open tab never switches code mid-form.

`/sw.js` is served with `Cache-Control: no-cache, no-store, must-revalidate` (see `next.config.ts`).

## Update strategy

1. Open tabs check for a new `sw.js` hourly (`UPDATE_CHECK_INTERVAL_MS`) and whenever the tab or app returns to the foreground.
2. When a new worker reaches `installed` (assets already downloaded) and an old one controls the page, `UpdateBanner` shows: *"A new version of EduNivo is ready."*, with **Update Now** and **Later**.
3. **Update Now** posts `SKIP_WAITING`. The new worker activates and `controllerchange` triggers a single reload into the new version. Auth (localStorage) and server data are unaffected, so the user stays signed in. **Later** hides the banner for this page load.
4. If the user closes the banner, the new version activates on its own once every EduNivo tab or window is closed.

## Testing

PWA behavior must be tested against a production build:

```bash
npm run build && npm run start        # http://localhost:3000
```

- **DevTools → Application → Manifest:** check fields and icons, and install with "Install" in the address bar.
- **DevTools → Application → Service workers / Cache storage:** see the registered worker and the `edunivo-*` caches. No `/api` entries should ever appear.
- **Install dialog:** clear `sms_next_pwa_install_dismissed_at` (localStorage) and `sms_next_pwa_install_shown` (sessionStorage), then log in. The dialog appears about 4.5 s after the dashboard loads, if Chrome considers the app installable. Check `chrome://flags` and site engagement if the event doesn't fire.
- **Update banner:** with a tab open, run `npm run build && npm run start` again, then focus the tab or run `(await navigator.serviceWorker.getRegistration()).update()` in the console.
- **Offline:** DevTools → Network → Offline, then reload a visited page (cached shell) and an unvisited one (`offline.html`).
- **iOS:** needs a real device or the Simulator on HTTPS. Use a deployed preview, or `next dev --experimental-https` for UI-only checks (the service worker is off in dev).

Install requires HTTPS. `localhost` is exempt.

## Future enhancements

- **Push notifications, server side.** The service worker already handles `push` (payload `{ title, body?, url?, tag? }`) and `notificationclick` (it focuses or opens EduNivo at `url`, same-origin only). Still missing: VAPID keys (`NEXT_PUBLIC_VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`), a subscribe UI that asks for notification permission, a per-user subscription collection, and sending via `web-push` when notices, homework or fees are created. Web push works on iOS 16.4+ for installed apps.
- **Manifest `screenshots`** (`form_factor: wide/narrow`) for the richer install UI on Android and desktop Chrome.
- **iOS splash screens** (`apple-touch-startup-image` per device size).
- **Offline read-only data** for low-risk, per-user data (e.g. timetable). This would need an explicit, user-scoped cache that is cleared on logout.
- **Background Sync** to queue attendance marking taken offline and send it when the connection returns.
- **App badging** (`navigator.setAppBadge`) for the unread chat count on the app icon.
- **`next/offline` `useOffline`** (experimental in this Next.js version) for an app-wide offline banner.
